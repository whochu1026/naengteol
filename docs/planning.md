# 냉털 기획서

> 역할: PM · 기획 · 개발을 한 사람이 수행한 MVP 기획 문서  
> 제품: 냉장고 식재료·유통기한 관리 웹 앱 **냉털**

---

## 1. 한 줄 요약

**“냉장고 구석에서 잊혀가는 식재료”** 문제를, 유통기한 기준으로 **등록 → 임박 확인 → 소비/폐기** 루프를 짧게 만들어 해결한다.

---

## 2. 해결하려는 문제

| 현실 | 왜 귀찮은가 |
|------|-------------|
| 산 재료를 메모장·머리속에만 둠 | 뭐가 있는지 한눈에 안 보임 |
| 유통기한을 따로 안 봄 | 열어보고 나서야 만료를 앎 |
| 먹었는지 버렸는지 기록이 없음 | “또 버렸네”만 반복되고 개선이 안 됨 |
| 같은 우유를 여러 번 등록 | 목록이 지저분해지고 포기하게 됨 |

엑셀 장부나 범용 투두로는 **날짜 임박 우선순위**와 **먹음/폐기 구분**이 약하다.  
냉장고라는 물리적 공간에 묶인 **짧은 루프**가 필요하다고 판단했다.

---

## 3. 대상 사용자

**1차 타깃:** 1인 가구·자취생·맞벌이 등, 장을 보고 나서도 재고를 머릿속으로만 관리하는 사람

**가정**

- 스마트폰·노트북 브라우저로 짧게 확인한다
- 처음엔 계정이 귀찮을 수 있어 **데모 로그인**으로 바로 체험 가능하게 한다
- 가족 공유·레시피 AI는 “있으면 좋지만” MVP에선 후순위

**페르소나 (요약)**

- 지현, 28세, 자취. 주 1회 장보기. “이번 주 안에 먹어야 할 것”만 빠르게 보고 싶다.
- 실패 경험: 요거트·잎채소를 자주 버린다. 앱이 무거우면 안 켠다.

---

## 4. 목표 / 비목표

### 목표 (MVP)

1. 식재료 **CRUD**가 안정적으로 동작한다
2. 유통기한 기준으로 **임박·오늘·이번 주**를 바로 본다
3. **먹음 vs 폐기**를 남겨 절약감을 수치로 본다
4. 등록 마찰을 줄인다 (빠른 재등록, CSV)

### 비목표 (이번 범위 밖)

- 가족 공유 냉장고, 실시간 동기화
- 바코드/영수증 OCR, 레시피 LLM
- 백그라운드 푸시(서버 푸시)·네이티브 앱
- 결제·구독

| P3 | 앱 오픈 시 알림 배너/브라우저 Notification | “안 열면 무용”은 인정하되 설정 UX는 명확히 |

## 6. 화면 구성

```text
[비로그인]
  /login  /signup

[로그인 후 AppShell]
  /dashboard     홈: 요약·오늘까지·이번 주·임박·최근 등록
  /plan          오늘·이번 주 먹을 것 (소비/폐기)
  /ingredients   식재료 목록·등록·합치기·CSV
  /ingredients/[id]  상세·수정
  /consumed      소비·폐기 이력
  /stats         통계·절약률          (계정 메뉴)
  /trash         휴지통               (계정 메뉴)
  /account       프로필·알림·비밀번호·탈퇴
```

**모바일:** 하단 탭 — 홈 / 먹을 것 / 식재료 / 소비 / 내 정보  
**데스크톱:** 상단 — 대시보드·먹을 것·식재료·소비 / 계정 메뉴에 통계·휴지통

### 사용자 시나리오 (핵심)

1. 장보고 와서 식재료 등록 (또는 빠른 재등록 → 유통기한만 입력)
2. 며칠 뒤 앱을 열면 상단 배너·대시보드에서 임박 확인
3. `/plan`에서 먹거나 폐기 처리
4. `/stats`에서 절약률 확인

## 7. API 목록 (요약)

인증·쿠키: `naengteol_token` (HttpOnly)

| 영역 | 메서드·경로 | 설명 |
|------|-------------|------|
| Auth | `POST /api/auth/signup\|login\|demo\|logout` | 가입·로그인·데모·로그아웃 |
| Auth | `GET\|PATCH\|DELETE /api/auth/me` | 내 정보·수정·탈퇴 |
| Auth | `PATCH /api/auth/password` | 비밀번호 변경 |
| Category | `GET /api/categories` | 카테고리 목록 |
| Dashboard | `GET /api/dashboard` | 요약 |
| Ingredient | `GET\|POST /api/ingredients` | 목록·생성 |
| Ingredient | `GET\|PATCH\|DELETE /api/ingredients/:id` | 상세·수정·휴지통 |
| Ingredient | `POST .../consume\|restore\|purge` | 소비(폐기)·복구·영구삭제 |
| Ingredient | `GET /stats\|alerts\|quick-templates\|export` | 통계·알림·템플릿·CSV |
| Ingredient | `POST /import\|merge\|bulk` | 가져오기·합치기·일괄 |

전체 스키마는 Swagger(`http://localhost:4000/api/docs`)와 `backend/openapi.yaml`을 따른다.

## 8. 데이터 모델 (기획 관점)

주요 리소스: **User**, **Category**(전역), **Ingredient**(사용자 소유)

- Ingredient `status`: `ACTIVE` → 보유, `CONSUMED` → 소비 완료, `DELETED` → 휴지통
- `outcome`: `USED`(먹음) / `WASTED`(폐기) — 통계용. soft delete와 분리
- 신선도(`freshness`)는 DB에 저장하지 않고, **Asia/Seoul 오늘** 기준으로 조회 시 계산

상세 필드·상태 전이는 [schema.md](./schema.md) 참고.

## 11. 왜 이 제품인가 (의사결정)

발문의 예시 중 **“냉장고 구석에서 잊혀가는 반찬/재료”**를 골랐다.

- 문제가 일상에서 반복되고, CRUD만으로도 가치가 나온다
- “날짜”라는 명확한 정렬·알림 축이 있어 기능 우선순위를 매기기 쉽다
- 동아리 회비 장부는 회계 규칙이, 영양제는 복용 스케줄이 더 복잡해 MVP 범위가 커지기 쉽다

기술 스택은 권장(Vue/Nest) 대신 **Next.js + Express**를 썼다.  
익숙한 풀스택으로 **기획↔구현 일치**와 완성도에 시간을 쓰기 위함이다. (권장 스택 강제 사항 아님)
